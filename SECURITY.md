## What "XSS" means (Kenneth asked)

XSS = Cross-Site Scripting. It is when an attacker gets their own code
running inside your page — for example by typing a script into a comment
box that the site then shows to other people without checking it. If it
runs, it can do anything the page can do: read what is on screen, steal
a login, click buttons as you. The defences here: React turns everything
you type into plain text (it never runs it as code), the server checks
every field before saving it, and the Content-Security-Policy header
tells the browser "only run scripts from this site" — so even if a bad
string slips through, a script from another site cannot run.

## What "SQL injection" means (Kenneth asked)

SQL is the language the database speaks. Injection is when an attacker
types database commands into a form field — for example typing
`' OR '1'='1` into a login box — hoping the app pastes their words
straight into a database question, so the question changes meaning and
lets them in, or dumps the whole user list. The defence here: the app
never builds a database question out of user words. It only ever sends
values through the Supabase client, which sends the question and the
values separately — the database treats values as data, never as
commands. There is no string-building of SQL anywhere in the app.

## What "CSRF" means ("cfr protection", Kenneth asked)

CSRF = Cross-Site Request Forgery. It is when a bad website tricks YOUR
browser into sending a request to Ace Studio while you are logged in —
for example a hidden form that posts "change my email" the moment you
open the bad page. Your browser would attach your login cookie, so the
server would think it was you. The defence: every form that changes
something must also send a secret token that only this site's pages can
read (double-submit cookie). The bad site cannot read the token, so its
forged request is rejected. SameSite=Lax on the login cookie is a second
layer.

## Things deliberately NOT done (and why)

- **No hand-rolled password hashing.** Supabase Auth does it (bcrypt).
  Hand-rolling it is how passwords leak.
- **No raw SQL from the app.** The migration file is the only SQL, and
  it is run once by a human in the dashboard, not by the app at runtime.
- **No "remember me" forever-login.** Refresh tokens last 30 days, then
  the user logs in again.
- **No password maximum above 8** — Kenneth specified 6–8. Flagged:
  an 8-character maximum is weaker than modern practice (longer
  passwords are harder to guess). Raising it later is a one-line change
  in `src/lib/security/validation.ts` (`PASSWORD_MAX_LENGTH`).

## Verification

- Unit tests: `src/lib/security/*.test.ts`,
  `src/lib/supabase/*.test.ts` — run with `bun run test`.
- Rate-limit checks (Phase C): 11 narration requests in a minute from
  one IP → the 11th is 429 `too_many_requests`; same for posting. Avatar
  upload of an HTML file labelled `image/png` → 400, nothing stored.
  Narration text starting with `<speak>` is escaped, never sent as SSML.
- Live checks (after wiring): login with 3 wrong passwords from one IP
  → 4th attempt is blocked for 15 minutes; signup with a 5- or
  9-character password → rejected; POST without a CSRF token → 403;
  profile picture over 2 MB or a `.exe` → rejected; user A cannot read
  user B's job (404 as if it does not exist).
- New checks from the 2026-11-07 review: a posting video URL pointing at
  a private/loopback address is rejected (SSRF); a checklist-only
  platform (e.g. Kick) never reports `configured: true`; mock narration
  is off when `NODE_ENV=production`; a narration pace outside ±50% is
  rejected; a stale running job (untouched 30 min) is marked failed
  while a live one is left alone.
- New checks from the Video 1 security pass (2026-11-08): a signup with
  the honeypot field filled gets the generic success but creates no
  account and burns no quota; a login with it filled gets a generic 401
  and records no failure (no lockout); a 3rd signup within 10 minutes
  from one IP is 429. Dependency audit: `bun run audit` (see the
  "Dependency scanning" row above — `bun audit` is blocked by the
  registry here, so the 2026-11-08 audit ran against OSV instead).
